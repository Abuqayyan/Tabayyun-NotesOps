1. ما هو النظام ولماذا

Tabayyun NotesOps هو نظام تشغيل داخلي للشركة (Company OS) يجمع في منصّة واحدة: إدارة المؤسسة (أقسام وموظفون وخطوط تبعية)، الصلاحيات الديناميكية، التحديثات اليومية، الاجتماعات ومحاضرها وبنود العمل، سلاسل الموافقات، قاعدة المعرفة، CRM متكامل، ولوحة تنفيذية بذكاء اصطناعي للمدير التنفيذي.

الفلسفة المعمارية: Modular Monolith (تطبيق واحد منظّم في وحدات) مناسب لأقل من 50 مستخدمًا على خادم واحد خلف Cloudflare. تخزين هجين: PostgreSQL كمصدر حقيقة للهوية والصلاحيات والأقسام والموافقات والتدقيق، وMongoDB للمحتوى والنشاط والمهام والملاحظات وCRM.

المبدأ الأساسي للصلاحيات: الكود يفحص الصلاحيات (permissions) وليس أسماء الأدوار. الأدوار مجرد «حِزم» قابلة للتعديل من الصلاحيات، تُسنَد للمستخدمين ضمن نطاق (الشركة كلها / قسم محدّد / مشروع محدّد). هذا يعطيك مرونة كاملة دون لمس الكود.

3. نموذج الصلاحيات (RBAC): الأدوار والنطاقات

الأدوار النظامية المُهيّأة مسبقًا

تُزرَع تلقائيًا، قابلة للتعديل، ومحميّة من الحذف فقط (is_system). يمكنك تعديل صلاحياتها أو إنشاء أدوار جديدة كليًا.

الدورالمفتاحالنطاق المعتادالوصف
Administratoradministratorglobalوصول كامل لكل المنصّة (كل الصلاحيات *).
Executiveexecutiveglobalرؤية على مستوى الشركة: لوحات، تقارير، نشاط، تدقيق، ذكاء، CRM (عرض).
Department Managerdepartment_managerdepartment:<id>إدارة ومراقبة قسم واحد — يُسنَد بنطاق القسم.
Employeeemployeeglobal أو departmentالوصول القياسي للموظف (تحديثات، مهام، اجتماعات عرض، موافقات رفع، معرفة، CRM كتابة).

النطاقات (Scopes) — الفكرة المحورية

كل تعيين دور = (مستخدم + دور + نطاق). النطاق يحدّد «أين» تسري صلاحيات الدور:

النطاقالمعنىمثال
globalالشركة كلهاالمدير التنفيذي يرى كل شيء.
departmentقسم واحد فقط«مدير قسم» بنطاق department:sales يدير المبيعات فقط.
projectمشروع واحد فقطصلاحيات محصورة بمشروع معيّن.
قاعدة ذهبية: نفس الدور «مدير قسم» يُسنَد لأشخاص مختلفين بنطاقات أقسام مختلفة، فيدير كلٌّ قسمه فقط — دون إنشاء أدوار مكرّرة.
المسؤول (is_admin): أي مستخدم يحمل العلم is_admin: true هو superuser يتجاوز كل فحوص الصلاحيات. استخدمه لحساب الإعداد الأول فقط، وامنح البقية أدوارًا مُحدَّدة.

5. فلو الإعداد خطوة بخطوة (Onboarding)

0. حساب الأدمن← 1. إعدادات الشركة← 2. الأقسام← 3. المستخدمون + الموظفون← 4. تعيين الأدوار بالنطاق← 5. التشغيل اليومي
0تجهيز حساب المسؤول الأول
  • أنشئ أول أدمن عبر سكربت البذر: docker compose exec backend python -m scripts.create_admin --email you@company.com --password '...' (ينشئ مستخدمًا بـ is_admin:true).
  • سجّل الدخول من /login. إن كان البريد (SMTP) مُفعّلًا سيصلك رمز OTP، وإلا فدخول مباشر بالبريد وكلمة المرور.
1إعدادات الشركة — التهيئة /settings-center
  • قسم «الشركة»: الاسم، الشعار، اللون، اللغة، المنطقة الزمنية.
  • «الإشعارات»: تفعيل البريد/داخل التطبيق وتكرار الملخّص. «الأمان»: مدة الجلسة، انتهاء الرمز، حد كلمة المرور، مدة OTP. «CRM»: المرحلة الافتراضية والعملة.
تحتاج صلاحية settings.manage للتعديل (المسؤول يملكها).
2إنشاء الأقسام — المؤسسة /organization ← تبويب «الأقسام»
  • أنشئ الأقسام الجذرية (مثل: المبيعات، التقنية، المالية، مكتب الرئيس التنفيذي).
  • للهيكل الهرمي: عيّن «القسم الأب» (parent_department_id) — مثل: مكتب الرئيس ← وحدات فرعية.
  • عيّن «مدير القسم» (lead_user_id) لاحقًا بعد إنشاء المستخدمين.
3المستخدمون ثم ملفات الموظفين (انظر القسم 6 للتفصيل)
  • أنشئ حسابات المستخدمين (دعوة/تسجيل)، ثم اربط لكل مستخدم ملف موظف فيه: المنصب، القسم الأساسي، والمدير المباشر (manager_id).
4تعيين الأدوار بالنطاق (انظر القسم 7)
  • المدير التنفيذي ← دور Executive بنطاق global.
  • مدير قسم ← دور Department Manager بنطاق department:<id>.
  • الموظفون ← دور Employee.
5انطلاق التشغيل اليومي (انظر القسم 8) — تحديثات، اجتماعات، موافقات، CRM، معرفة.
كل إجراء يُسجَّل: كل عملية إنشاء/تعديل/حذف تُسجَّل في سجل التدقيق وتظهر في موجز النشاط تلقائيًا.

6. إضافة الأقسام والموظفين وخطوط التبعية

أ) الأقسام

المؤسسة /organization ← «الأقسام» ← «قسم جديد». الحقول:

الحقلالمعنى
nameاسم القسم (فريد).
descriptionوصف اختياري.
parent_department_idالقسم الأب (للهيكل الهرمي).
lead_user_idمستخدم مدير القسم.

ب) المستخدمون

أنشئ حساب لكل شخص (بريد + كلمة مرور). الموظف لا «يصير موظفًا» في الهيكل إلا بعد إنشاء ملف موظف له.

ج) ملفات الموظفين وخطوط التبعية

المؤسسة ← «الموظفون» ← «موظف جديد». الحقول:

الحقلالمعنى
user_idالمستخدم المرتبط (حساب موجود).
positionالمسمّى الوظيفي.
primary_department_idالقسم الأساسي.
manager_idالمدير المباشر (ملف موظف آخر) — هذا هو خط التبعية.
employment_statusالحالة (active افتراضيًا).
لماذا خط التبعية (manager_id) مهم؟ لأنه عمود فقري لِـ: توجيه الموافقات («مدير مقدّم الطلب»)، رؤية المدير لتحديثات فريقه، وتجميع التقارير من القسم → الإدارة → الشركة.
عضوية متعددة (اختياري): يمكن للموظف أن يكون عضوًا في أكثر من قسم عبر «أعضاء القسم» (department_members) مع تحديد القسم الأساسي.

ترتيب صحيح موصى به

أنشئ الأقسام← أنشئ المستخدمين← أنشئ ملفات الموظفين (بدون مدير)← اربط manager_id← عيّن lead_user_id للأقسام
أنشئ المدراء أولًا ثم اربط مرؤوسيهم بهم، أو أنشئ الجميع ثم حرّر manager_id. لا يمكن لموظف أن يكون مدير نفسه.

7. تعيين الأدوار بالنطاق الصحيح

المؤسسة /organization ← «الأدوار والصلاحيات (RBAC)». لكل تعيين تختار: المستخدم، الدور، نوع النطاق، ومعرّف النطاق.

الشخصالدورالنطاقالنتيجة
الرئيس التنفيذيExecutiveglobalيرى كل الشركة (لوحات/تقارير/نشاط/تدقيق/ذكاء).
مدير المبيعاتDepartment Managerdepartment: المبيعاتيدير قسم المبيعات فقط (تحديثات/اجتماعات/موافقات/CRM كامل/تقارير القسم).
موظفEmployeeglobalتحديثات يومية، مهام، اجتماعات عرض، رفع موافقات، معرفة، CRM كتابة.
مسؤول النظامAdministrator أو is_adminglobalكل شيء.
مهم — قاعدة النطاق: عند اختيار نطاق «قسم» أو «مشروع» يجب تحديد scope_id. النطاق العام (global) لا يحتاج معرّفًا.

إنشاء دور مخصّص

المؤسسة ← «الأدوار» ← «دور جديد»: امنحه مفتاحًا واسمًا واختر مجموعة الصلاحيات من الكتالوج. مثال: «مسؤول معرفة» = kb.view + kb.create + kb.edit. الأدوار النظامية قابلة للتعديل لكنها محميّة من الحذف.

كيف يقرّر النظام؟

user_can(user, permission, resource) =
  is_admin? → allow
  else: هل لدى المستخدم تعيين دور يحوي permission
  ونطاقه يغطّي قسم/مشروع resource (أو global)؟ → allow / deny

الواجهة تُخفي ما لا تملكه من عناصر التنقّل والأزرار، والخادم هو الحكم النهائي (يرفض بـ 403 ويظهر للمستخدم حالة ودّية).

8. التشغيل اليومي (Daily Loop)

الموظف

  1. التحديث اليومي /daily-updates: اكتب اليوم/غدًا/المعوّقات (قابل للتعديل في نفس اليوم).
  2. المهام: نفّذ مهامك (بما فيها المهام المتولّدة من بنود اجتماعات).
  3. المعرفة /knowledge: اقرأ السياسات والأدلة.
  4. الموافقات /approvals: ارفع طلبًا (إجازة/شراء/…)، وتابع حالته.

مدير القسم

  1. راجع تحديثات الفريق/القسم اليومية.
  2. أدر اجتماعًا /meetings: سجّل المحضر (قرارات/نقاط نقاش) وأضف بنود عمل — كل بند يُنشئ مهمة بمالك.
  3. قرّر الموافقات الموجّهة إليك عبر سلسلة التبعية.
  4. أدر CRM قسمك (شركات/عملاء/فرص) وصدّر القوائم CSV/XLSX.

الرئيس التنفيذي

  1. افتح اللوحة التنفيذية /executive: صحة الشركة والأقسام، المخاطر، التصعيدات، الموافقات المعلّقة، خط أنابيب CRM والتوقعات، توصيات ذكية.
  2. الذكاء داخل CRM: رؤى الإيرادات والصفقات المتعثّرة.
  3. مركز العمليات /ops: صحة النظام والجدولة والأخطاء.

سلسلة الموافقات — مثال

موظف يرفع طلبًا← المدير المباشر← مدير الإدارة← الرئيس التنفيذي← معتمَد ← آثار جانبية (مهمة/إشعار)
تُحدَّد كل خطوة بقاعدة: «مدير مقدّم الطلب» أو «دور» أو «شخص»، مع تذكيرات SLA عبر المجدول.

9. رحلات المستخدمين حسب الدور

① الرئيس التنفيذي
الشاشات: التنفيذي · CRM (ذكاء/خط أنابيب) · العمليات · جرس الإشعارات.
الصلاحيات: company.dashboard.view, intelligence.view, report.view_company, crm.*.view, ops.view, audit.view (عبر دور Executive).
② مدير القسم
الشاشات: التحديثات اليومية · الاجتماعات (+MOM) · الموافقات · CRM · المؤسسة (عرض).
الصلاحيات: دور Department Manager بنطاق قسمه — تحديثات الفريق/القسم، اجتماعات كاملة، موافقة، CRM كامل داخل النطاق، تقارير القسم، معرفة.
③ الموظف
الشاشات: اللوحة · المهام · التحديثات اليومية · الاجتماعات (عرض + بنوده) · المعرفة · CRM (ضمن النطاق) · رفع موافقات.
الصلاحيات: دور Employee — task.manage, daily_update.submit, meeting.view, approval.create, kb.view, crm.*.create/edit.
④ مستخدم CRM (مبيعات)
الرحلة: أنشئ شركة وجهة اتصال ← أنشئ عميلًا محتملًا ← حرّكه عبر المراحل ← حوّله إلى فرصة ← أدِرها على لوحة خط الأنابيب ← تابع التوقعات والذكاء (صفقات متعثّرة، متابعات، إيراد معرّض للخطر).

عوامل مشتركة

  • بحث شامل: Ctrl/⌘ + K — مُصفّى بالصلاحيات، مع بحثات حديثة.
  • مركز الإشعارات: جرس بعدّاد غير مقروء + صفحة /inbox بتصفية وأرشفة.
  • تصدير: أزرار CSV/XLSX على الموافقات والاجتماعات وCRM والمعرفة — مُدقّقة على الخادم.

12. أفضل الممارسات وقائمة تحقّق الإطلاق

أفضل الممارسات

  • أقل امتياز: امنح أضيق دور يكفي. استخدم is_admin لحساب الإعداد فقط.
  • النطاق قبل الدور: «مدير قسم» دائمًا بنطاق قسمه، لا global.
  • خطوط التبعية أولًا: اضبط manager_id بدقّة — تعتمد عليه الموافقات والتقارير.
  • أدوار مخصّصة بدل تعديل النظامية كثيرًا: أنشئ أدوارًا جديدة لاحتياجات خاصة.
  • راجع سجل التدقيق دوريًا (audit.view).
